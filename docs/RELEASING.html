Releases and versioning

The root VERSION file is the application version. Every page displays it in the footer, and deployment checks confirm that Heroku is serving the expected version. The initial version is 1.0.0.

Update the version with every change

Include a version increase in every change, including maintenance, workflow and documentation updates. Use exactly three numbers, MAJOR.MINOR.PATCH, without a prefix, suffix or leading zeroes. Make the version greater than the target branch's current version. Keep the same version when promoting that change to another branch, provided it is higher than the target branch's version.

ComponentWhen to increase itExample
MajorIncompatible changes to existing behavior or interfaces1.4.2 → 2.0.0
MinorBackward-compatible features1.4.2 → 1.5.0
PatchFixes, maintenance, workflow or documentation changes1.4.2 → 1.4.3

Reset lower components when increasing a higher component. CI checks pull requests against their target commit, and pushes against the previous commit on that branch. A changed tree with an unchanged or lower version fails CI. A promotion with no file changes retains its version. Later edits within the same unmerged pull request can share its planned release version.

.github/workflows/ci.yml deploys only after version validation, Brakeman, the dependency audit, RuboCop, RSpec, and JavaScript tests pass. Pull requests and the test branch run checks without Heroku deployment. A failed, skipped or cancelled prerequisite prevents deployment.

Deployments are serialized per branch. Superseded commits are skipped, and Git pushes use the exact commit that passed CI. The script then checks that Heroku's release succeeded, the active slug matches that commit, /up responds successfully, and the homepage footer shows the expected version. Heroku's Procfile release command applies database migrations. A failed release leaves the previous release active; a health-check failure fails CI and needs investigation.

Credentials and operations

Deployment requires the repository's Actions secret HEROKU_API_KEY, set to a dedicated Heroku OAuth authorization that can authenticate to Heroku Git and read release/slug metadata. The literal read,write scopes failed verification. Heroku's protected app scopes also grant access to runtime configuration and secrets for all apps accessible to the authorized account; obtain explicit approval for that exposure before provisioning. For narrower access, use a dedicated automation account with access only to the intended apps. Verify Git and release/slug access before activation. Revoke or rotate the authorization independently of local CLI login, then replace the GitHub secret. Keep tokens out of source files and logs. The deployment workflow does not create or upgrade dynos or databases.

GitHub Actions must be enabled for this repository. If organization policy disables Actions, an organization administrator must allow this repository before checks or deployment can run; a repository administrator cannot override that policy.

Existing Vercel deployment remains in its separate workflow. This document describes the Heroku CI gate; Vercel's separate workflow is not gated by these jobs.

For a fresh database, run heroku run 'bundle exec rails db:seed' -a APP after migration to install reference terms. Seeds preserve existing named terms. For rollback, use a compensating change with a higher version, or an explicit Heroku rollback; database migrations are not reversed by code rollback.
